# tcp_sticky_packet

用状态机解析 TCP 字节流，解决粘包与拆包问题的 C 语言实现（Linux）。

## 为什么需要它

TCP 是字节流协议，不保留消息边界。发送方调用 3 次 send()，
接收方一次 recv() 可能读到全部内容（粘包），也可能只读到半个消息（拆包）。
本项目用「帧头 + 长度字段 + 校验 + 帧尾」的应用层协议配合状态机解析，
把无边界的字节流还原成一条条完整的消息。

## 帧格式

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| 帧头 | 2 字节 | 0xAA 0x55，用于定位一帧的起点 |
| 长度 | 2 字节 | 数据区字节数，网络字节序（大端），上限 1024 |
| 数据 | 0 ~ 1024 字节 | 实际负载 |
| 校验 | 1 字节 | 数据区逐字节异或 |
| 帧尾 | 1 字节 | 0x0D |

一帧总长 = 4 + 数据长度 + 2 字节。

## 状态机做了什么

解析时不能假设「一次 recv 就是一帧」。状态机负责记住**当前收到哪里了**：

    IDLE（等 0xAA）→ HEADER（等 0x55）→ LENGTH（收 2 字节长度）
    → DATA（收满长度指定的字节）→ CHECK（收校验位）→ TAIL（收 0x0D 并校验）

- 数据没收满就停在 DATA 状态，等下一次 recv 接着收 —— 解决**拆包**
- 一帧收完立刻回到 IDLE，把同一批数据里剩下的继续解析 —— 解决**粘包**
- 长度越界、校验失败、帧尾不对，丢弃该帧并重新同步

每个连接持有独立的解析上下文，不使用全局变量。

## 编译与运行

    make              # 编译 server / client / demo_sticky
    make run-server   # 终端 1：启动服务端
    make run-sticky   # 终端 2：一次发送 3 帧（制造粘包）
    make run-split    # 终端 2：一帧分两次发送（制造拆包）
    make tcpdump      # 终端 3：抓包观察

## 怎么验证

1. **粘包**：`make run-sticky` 一次 send 34 字节含 3 帧，服务端一次 recv 后连续打印 3 行
2. **拆包**：`make run-split` 先发 6 字节半帧，停顿 1 秒再发剩余部分，服务端停顿后才打印
3. **抓包**：`sudo tcpdump -i lo -nn -A 'port 8888'`，数据区能看到 `AA 55 00 05 Hello 42 0D`

## 关键实现与难点

- **长度字段必须转网络字节序**：x86 是小端机，len=5 在内存里是 `05 00`，
  直接发送会让对端按大端解析成 0x0500 = 1280，超过上限被判非法帧，一帧都收不到。
- **校验位要单独收**：数据的最后一个字节不是校验位。收满数据后还要再读 1 字节校验、
  1 字节帧尾，否则整个解析会错位一格。
- **一次 recv 要循环解析**：收到的数据可能包含多帧，解析完一帧后必须继续处理剩余字节，否则丢帧。
- **每个连接独立上下文**：解析状态放在 per-connection 结构体里，避免多连接互相干扰。

## 验证记录

字节序对比：在同一条 TCP 连接里连续发两帧，内容相同、仅长度字段字节序不同。

    $ printf '\xaa\x55\x05\x00Hello\x42\x0d' >&3     # 长度字段小端 05 00
    bad frame, resync                                 # 被解析成 1280，超过上限丢弃
    $ printf '\xaa\x55\x00\x05Hello\x42\x0d' >&3     # 长度字段大端 00 05
    Received (5 bytes): Hello                         # 正常解析

结论：多字节整数上网络前必须用 htons() 转成网络字节序（大端）。

粘包验证：`make run-sticky` 一次发送 34 字节含 3 帧，服务端一次 recv 后连续打印 3 行，
说明解析循环正确处理了一包多帧的情况。
